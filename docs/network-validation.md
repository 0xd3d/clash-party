# Network validation procedure

Keep operating policy separate from software. Start from the chosen, known egress and record time, app/core PID, effective TUN state, DNS upstream routing, system resolver settings and configured exceptions. Avoid raw credentials, browser cookies, signed URLs and private logs in shared evidence. Do not stop a required VPN merely to obtain a baseline; mark unavailable baseline information as unavailable.

## Independent browser tests

- [BrowserLeaks DNS](https://browserleaks.com/dns) resolves randomly generated IPv4-only and IPv6-only names. Record resolver addresses, operator and country, rather than just the server count.
- [DNSLeakTest](https://www.dnsleaktest.com/) Extended Test runs six rounds. Use it as an independent authoritative-DNS observation, then compare with the expected resolver policy.
- [IPLeak](https://ipleak.net/) cross-checks HTTP IP, WebRTC/STUN and DNS; record whether the IPv6 test actually completed. Do not turn on torrent or location testing when unnecessary.
- [BrowserLeaks WebRTC](https://browserleaks.com/webrtc) checks ICE candidates. Under [RFC 8828](https://www.rfc-editor.org/rfc/rfc8828.html), a server-reflexive address matching the proxy egress is different from an ISP address. A browser-generated `.local` mDNS host identifier is not a revealed LAN/public IP. Do not grant camera/microphone access merely for this test.

These sites reveal only the traffic generated by that browser/session. Different recursive DNS IPs or Anycast countries alone do not prove that the local ISP saw the DNS query. An IPv6 resolver address is not the client IPv6 address. No result proves that an IP is residential, never abused, or guaranteed access to a particular model/service.

## Native transport checks

Compare fresh UDP and TCP DNS sockets against localhost, a public resolver and the current LAN resolver. Fake-IP answers prove local interception, not which upstream handled the final name. Real replies from a hardcoded LAN resolver demonstrate a bypass even when ordinary system DNS is local. Keep this separate from a browser's unique authoritative-query results.

Check explicit HTTP-proxy and TUN HTTPS paths, without disabling certificate verification. Record the remotely observed address and TLS result. Test actual client IPv6 transport when available; a timeout or TLS failure is inconclusive, not a pass. Check that proxy ports remain loopback-only, and recheck expected LAN IP reachability and domain-policy exceptions.

For the optional macOS PF guard, require the active dedicated anchor, enabled PF and before/after fresh-socket evidence, not just a timeout. Confirm local DNS, DoH, HTTPS and LAN services still work. Preserve existing states and all unrelated firewall rules. See the guard README for its explicit lifecycle and Apple's PF compatibility restrictions.

## Platform and lifecycle checks

On Windows hardware, verify administrator and ordinary launches, WFP/adapter DNS, two active interfaces, browser Secure DNS, IPv4/IPv6, sleep/resume, startup/mode selection, manual retry and normal exit. Preserve user TUN preferences on permission failure. NRPT, enterprise security policy and competing VPNs require their own environment checks.

On macOS, verify the per-service DNS journal, new/removed interfaces and normal exit/restart recovery. Forced process kill cannot run app exit handlers. Real interface switching, sleep, AirDrop, Internet Sharing and Xcode device connectivity are separate tests that must be marked untested when not exercised.

Native CI runners verify source checks, binary architecture, packaged resources and native module loading. They do not reproduce a user's physical network, browser profiles, company gateway or chosen proxy server. Release manifests explicitly avoid claiming that certification.
